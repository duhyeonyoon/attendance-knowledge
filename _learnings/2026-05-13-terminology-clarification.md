# 2026-05-13 — 핵심 용어 정정: 근무 스케줄 / 근무 계획 / 근무 템플릿

두현님 피드백으로 핵심 용어 관계가 명확해짐.

## 정정 내용

```
근무 스케줄 = 근무 계획 (동의어, UI에 따라 달리 표현)
근무 계획의 종류 = 근무 템플릿 (재사용 가능한 타입)
```

### 관계도

```
[근무 템플릿] (재사용 가능 타입)
   예: "주간 9-18 템플릿", "야간 22-6 템플릿", "휴일 템플릿"
        ↓ (특정 일자/구성원에 적용)
[근무 계획 = 근무 스케줄] (인스턴스)
```

## 이 정정이 풀어주는 명명 헷갈림 (모두 정합)

| 코드/UI 표현 | 정합한 해석 |
|------|------|
| `personal_work_template_management` | 개인별 근무 계획(스케줄)의 **종류** 관리 |
| `WorkPlan` AttendType (캘린더) | 근무 계획 = 미래의 근무 스케줄 |
| `TM_DD_WORK_PLAN` 테이블 | 일별 근무 계획/스케줄 (마스터 + 인스턴스 모두 가능, prefix로 구분) |
| `TM_EMP_WORK_PLAN` | 구성원 근무 계획/스케줄 (개인스케줄 저장) |
| `TM_WORK_GRP_WORK_PLAN` | 근무그룹 근무 계획/스케줄 (그룹스케줄) |
| 어드민 #5의 "근무 템플릿" 탭 | 근무 계획의 종류 정의 (마스터) |
| 어드민 #6의 "그룹스케줄" 탭 | 그룹 단위로 어떤 종류(템플릿)의 근무 계획을 적용할지 |
| 어드민 #11의 "개인 근무 스케줄 관리" | 개인 단위로 적용된 근무 계획(스케줄) 관리 |
| 사용자 U11 "근무스케줄 메인페이지" | 사용자의 근무 계획 보기/수정 |
| 사용자 U19 "근무계획 변경 신청서" | 본인의 근무 계획(스케줄) 변경 신청 |

→ **모든 명명이 일관**. 제가 이전에 "명명 불일치"로 적은 것이 사실은 정합 (template = 종류, schedule = 적용된 계획).

## 우선순위 룰 재해석

이전에 정리한 룰들이 더 명확해짐:

- **개인스케줄 > 그룹스케줄 우선순위**: 개인 단위로 적용된 근무 계획이 그룹 단위로 적용된 것보다 우선
- **근무 템플릿 fork**: 클라이언트 공통 템플릿(종류)을 그룹에서 수정 시 새 종류 row로 분리 (원본 보존)
- **변경 출처 3가지** (#11): 모두 "개인 근무 계획"을 만드는 출처 (근무계획변경 신청서 / 직책자 변경 / 대체근무 신청서)

## 인사이트: 도메인 명명 패턴

이 정정으로 attendance 도메인의 명명 일관성을 다시 확인:
- **타입(종류) / 인스턴스(적용)** 분리 패턴: 휴가 제도 vs 휴가, 근무 템플릿 vs 근무 계획, 기타근무 항목 vs 기타근무 사용
- 코드는 **type 단어** (template, system, item, rule)와 **instance 단어** (plan, use, reg)로 일관 구분
- UI는 사용자 친화적 한국어로 변환 (template = 템플릿/종류, plan = 계획/스케줄)

→ 다음에 명명 헷갈리는 것 발견 시 **type vs instance** 패턴을 먼저 의심.

## 운영 가이드

이제 마스터 Skill이 사용자/고객사 질문에 답변할 때:
- "근무 스케줄"과 "근무 계획"이 같은 말임을 인지
- "근무 템플릿"은 그 종류를 정의하는 마스터임을 인지
- 코드/UI 명명을 보고 "type 정의인지 / instance 적용인지" 분류 가능

## 핵심: 작은 용어 정정이 큰 인사이트

두현님의 한 줄짜리 정정이 여러 문서의 명명 헷갈림을 한 번에 해소. 일관된 도메인 모델이 있다는 신호. **앞으로도 작은 용어 질문/정정을 적극 환영**.
