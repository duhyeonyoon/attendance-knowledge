## 큰 발견

### 1. 휴가 도메인 = 별도의 큰 서브 도메인
근무(work) 도메인과 분리된 독립 서브 도메인. 4영역 + 연차촉진까지 합치면 attendance에서 가장 큰 영역. 휴가그룹과 근무그룹이 별도로 운영됨 (같은 구성원이 다른 그룹에 속할 수 있음).

### 2. 휴가 도메인의 데이터 흐름
```
[마스터 정의 (#12)] → [그룹 정책 (#13)] → [운영 (#14)] → [사용자 사용 (U8)]
```
이 계층이 일관되게 적용됨. 다른 attendance 영역에서 본 패턴(마스터-그룹-사용)이 휴가에서도 동일.

### 3. 연차 vs 연차 외 = 거의 모든 곳에서 구분
- 어드민 #12에 별도 페이지 (연차 제도 / 연차 외 휴가 제도)
- 어드민 #14에 4개 탭 (연차 보유 / 연차 외 보유 / 연차 사용 / 연차 외 사용)
- 사용자 U8에 별도 표시 영역
- 정산 방식도 다름 (연차는 의무사용/이월/보상, 연차 외는 보상/이월/소멸)
- 연차촉진은 **연차에만** 적용 (연차 외는 X)

### 4. 임시저장 패턴이 휴가그룹에도 동일
근무그룹에서 본 `init-save → temp-save → 확정` 패턴이 휴가그룹에도 그대로 적용. `LeaveGroupSettingController`도 같은 endpoint 구조.

### 5. 연차 외 휴가의 사용자명/어드민명 분리
연차 외 휴가 제도는 **사용자에게 보이는 이름과 어드민이 보는 이름을 별도 설정 가능**. 운영 편의 (예: 사용자 = "특별 휴가", 어드민 = "직원 행사 보상")

### 6. 수동 휴가 등록의 3분기 모달
수동 등록 시 일부만 신청 가능한 경우:
- 정상 + 유효성 실패 → [이어서 진행]
- 정상 + 연차 부족 → [제외하고 등록]
- 연차 부족만 → [초과 사용으로 등록]

세 가지 케이스가 코드/UI에 명확히 구분됨. 운영팀이 자주 마주칠 분기.

### 7. 1년 미만 연차의 2가지 부여방식
- **선부여 (1건)**: 11개 한꺼번에 부여 (같은 사용기간)
- **다건 분할**: 매월 1건씩 별도 사용기간/개수

UI도 다름:
- 선부여 → 안내 문구 없음
- 다건 → "남은 1년 미만 연차를 먼저 확인합니다." 안내 + 상세 모달

### 8. 휴가 일수 계산 공식
```
휴가 일 수 = 휴가 분 수 / (일소정근로시간 × 60)
- 소수점 둘째자리까지 반올림
- 소수점 마지막 자릿수 0 생략
```

이 공식은 모든 화면에서 일관되게 적용. glossary에 명시함.

### 9. 출근 가능시간의 동적 계산
휴가 신청 시 "당일/익일 출근가능시간 이내" 검증:
- 시스템 기본 = 익일 06:00
- 익일 템플릿 고정출근 있으면 = (익일출근 - 2시간)

이전 자정 cutoff 학습(`ValidWorkDayResolver`의 -3시간/6시 규칙)과 비슷한 동적 계산. 휴가는 -2시간/6시.

### 10. 연차촉진은 별도 큰 흐름
4탭 워크플로우 (대상자 → 통지 → 사용시기 지정 → 노무수령거부 현황) + 시스템 전자문서 연계 + 노무수령거부 팝업의 디바이스별 노출 룰. **사용자 측 U13과 짝**이라 별도 deep-dive 가치 있음.

## 좋은 설계 패턴 인사이트 (질문 #1에서 배운 것)

**"단위가 모호할 수 있으면 더 작은 단위로 강제"** — 휴가 지급은 시간 단위로만 가능하게 함으로써:
- 회사/사람마다 다른 소정근로시간에 의존하지 않음
- 입력 시 항상 정확한 양 보장
- 사후 계산 시(휴가 일수 표시) 분 → 일 변환 공식 적용

이 패턴은 attendance 도메인 곳곳에서 발견되는 설계 철학으로 보임 (근무 시간도 분 단위 저장 등). 다른 영역 deep-dive 때 비슷한 케이스 발견 시 인용 가능.
