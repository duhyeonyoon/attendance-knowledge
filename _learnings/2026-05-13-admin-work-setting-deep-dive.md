### 2. 4가지 영역의 상속 패턴이 미묘하게 다름
| 영역 | 그룹이 생성 가능? | 비활성/삭제 동작 |
|------|------|------|
| 휴일 | ✅ (그룹 휴일) | 비활성 → 그룹 영향 |
| 출근지 | ✅ (그룹 출근지) | 비활성 → 그룹 영향 |
| 근무 템플릿 | ✅ (그룹 템플릿) + fork | 비활성 → 그룹에서 추가 불가 |
| 기타근무 항목 | ❌ (클라이언트만) | **DELETE cascade** → 그룹 매핑까지 삭제 |

기타근무 항목만 다른 동작. 운영 시 주의.

### 3. `/time/dd-work-plans` endpoint의 다용도
같은 endpoint prefix가 3개 컨텍스트에서 사용:
- `/time/dd-work-plans` — 클라이언트 근무 템플릿 (이 영역)
- `/time/work-grps/{workGrpId}/dd-work-plans` — 근무그룹 그룹스케줄
- 일별 근무계획 적용본 (`TM_DD_WORK_PLAN`)

→ `TM_DD_WORK_PLAN` 테이블이 마스터/그룹/일별을 모두 저장하는 다용도 테이블로 추정. 분기 컬럼 [TBD].

### 4. 회사별 옵션 = 새 row 생성 패턴
POST `/time/company-time-option`이 "ID 있어도 새 UUID 부여하여 새로 생성"이라는 점이 흥미로움. **이력 보존 패턴**으로 추정 (한 주 시작이 바뀐 이력을 추적하기 위해?).

### 5. 한 주 시작 변경 제약
"이미 설정된 회사 또는 근무 집계가 있는 회사인 경우 변경할 수 없다" — 집계 무결성 보호. 마감과 비슷한 일관된 보호 메커니즘.

### 6. 근무 템플릿 fork
공통 템플릿을 그룹에서 수정 시 그룹용 새 row 생성. 원본 보존 + 다른 그룹 영향 차단. **좋은 설계 패턴**.
